PanelSafe: what a 92% score was actually measuring

A detection pipeline for electrical panel audits, the silent label-ordering bug that made its headline metric meaningless, and the controlled ablation that deleted my own optimisation.

Role
Sole engineer — ML, DevOps, architecture
Period
July 2025 — ongoing
Stack
Python · YOLOv8 · PyTorch · OpenCV · Docker · Kubernetes · Proxmox
Status
Field calibration
1.0

The bottleneck is documentation, not diagnosis

Auditing a consumer unit is not hard for a qualified electrician. Documenting it is. Every inspection means photographing the board, identifying each protective device by type and rating, transcribing it, and producing a single-line diagram that matches. On a working day that is twenty minutes of clerical work per panel, done on a phone, in a hallway, in bad light.

I was the person doing it. That is the only reason this project has a defensible dataset: I had the access, and I knew what each device was without guessing.

Remark

Domain access is the moat. A general-purpose CV engineer cannot obtain eighty photographs of live Spanish consumer units, and could not label them correctly if they did.

2.0

The 92% that meant nothing

The model scored 92% on real-world validation images and was visibly wrong in the field, confidently calling differentials MCBs and MCBs differentials. The intuitive reading was resolution: tiny, near-identical objects on a high-resolution image. So the first fix attempted was slicing-aided inference — tiling the panel into overlapping windows, running detection per tile, merging with NMS.

It did not help, because the premise was wrong. The real cause was that the annotation tool wrote its class indices from a classes.txt whose ordering disagreed with the data.yaml the training run read. Every hand-labelled real image was permuted — not a two-class swap, but a full six-class rotation. The model had faithfully learned the permutation.

label_remap.py
# What the annotation tool wrote vs. what training actually read
CLASSES_TXT = ["RCD", "MCB", "MAINBREAKER", "OVERSURGE", "OTHER", "RCD_SI"]
DATA_YAML   = ["MCB", "RCD", "RCD_SI", "MAINBREAKER", "OVERSURGE", "OTHER"]

# Every real annotation had to be rewritten through this map
REMAP = {written: DATA_YAML.index(name)
         for written, name in enumerate(CLASSES_TXT)}
# -> {0: 1, 1: 0, 2: 3, 3: 4, 4: 5, 5: 2}

# Synthetic labels were generated programmatically against data.yaml,
# so they were correct all along -- which is exactly why the bug hid:
# the corrupted subset was small enough to look like ordinary noise.

Scored against corrected labels, that same 92% became roughly 6%. The metric had never measured accuracy. It measured agreement with a broken ground truth.

3.0

The ablation that removed my own work

With the labels fixed, the slicing optimisation was re-run as a controlled ablation rather than assumed to help. Breakers are small objects in a wide frame, so tiling is the textbook move and I had already written it.

It measurably reduced accuracy, so it was cut from the production pipeline. Tiling severs the rail context that the spatial layer and the sequence decoder both depend on, and merge artefacts at tile boundaries split single wide devices in two. The dependency is still listed in requirements.txt, annotated with why it is deliberately unused — so that nobody, including a future me, re-adds it on intuition without re-running the experiment.

Remark

An optimisation that is obviously correct and measurably wrong is the most expensive kind. The harness exists so the argument is settled by a number rather than by whoever is most confident.

4.0

Eighty photographs, and a generator to make them behave like eight hundred

The primary dataset is 80+ high-resolution field captures, all mine, all annotated by someone who can read the device markings. That is enough to prove a concept and nowhere near enough to train a detector that generalises across board layouts.

So the annotation bottleneck got engineered around rather than paid for. The synthetic pipeline crops annotated devices out of real panels, generates alpha masks to strip the original background, and pastes them back onto empty panel backgrounds in randomised configurations. Labels come out of the paste operation for free, because the pipeline knows what it placed and where. The training library expanded roughly tenfold.

The synthetic set teaches the model what a breaker looks like in arbitrary company. The real set teaches it what a breaker looks like under a hallway bulb.

5.0

A DIN rail has grammar, so the decoder should too

A detector returns independent boxes with independent confidences. A breaker board is not independent. Devices sit on a rail in sequence, they occupy whole module widths, and the sequence obeys rules — a residual-current device protects the branches downstream of it, the main disconnect comes first, ratings descend in a particular way.

So detections pass through a spatial heuristic layer that snaps them to rail geometry and module boundaries, then through an HMM whose states are device types and whose transitions encode that physical grammar. Viterbi selects the most probable legal sequence rather than the highest-scoring independent set. A confident wrong device that violates the rail’s logic loses to a less confident device that fits.

This is the part that does not come out of a paper. It is domain knowledge encoded as a prior, and it is available to me because I have wired the boards.

Downstream

The decoded sequence is what PanelSafe Unifilar compiles into a regulatory single-line diagram. The grammar is what makes that compilation possible at all.

6.0

Inference as a service, not a notebook

The inference API is containerised and deployed as a microservice on my own hardware — Proxmox with GPU passthrough underneath, Kubernetes above. A CI pipeline lints, runs the unit tests, and builds the container on every push to main.

Dockerfile
FROM python:3.10-slim
WORKDIR /app

# System libraries OpenCV links against
RUN apt-get update && apt-get install -y \
    libgl1-mesa-glx \
    libglib2.0-0 \
    && rm -rf /var/lib/apt/lists/*

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY src/ ./src/
COPY models/ ./models/

EXPOSE 8000
CMD ["uvicorn", "src.main:app", "--host", "0.0.0.0", "--port", "8000"]
Remark

Self-hosted on purpose. Owning the path from photograph to served prediction is the difference between a model and a product, and it is cheaper than renting GPUs to find that out.

7.0

Shipping the honest version

Field testing still shows domain drift on panels with the cover off, where exposed wire nests dominate the frame, and on boards whose markings are handwritten, faded or absent. That is a data problem with a data answer, not a reason to retune the loss function.

So rather than hold the product until full automation works, panelsafe.cv is live and free, EU-hosted, running human-in-the-loop risk scoring. The model proposes, the electrician confirms or corrects, and every correction is a labelled field example drawn from exactly the distribution the model is weakest on.

It is a data-collection instrument disguised as a useful free tool, and it is the only route I can see from eighty photographs to a corpus that supports full automation. Target for that is 2027.
